# 自动扩缩：Relax 服务负载基线

默认 `policy_mode=service`。策略参考官方 Relax 提交
[`6a2ad57`](https://github.com/redai-studio/Relax/tree/6a2ad57ec46a0fb02cec13dc5c2bd7077ecd64a8)，
重点对照 `relax/utils/autoscaler/scaling_decision.py`、`metrics_collector.py` 和 `autoscaler.yaml`。
复用其判据及增量公式，接入现有 vLLM 指标和 ElasticRollout 生命周期；不引入 Relax 运行时依赖。

## 扩容

以下任一条件持续 30 秒即考虑扩容，条件分别计时，不能靠不同高压信号交替维持：

- 平均 KV 使用率大于 0.85。
- 每副本平均排队请求大于 10。
- 请求排队 P95 大于 5 秒，或 P95 落在 `+Inf` 桶。
- TTFT P95 大于 10 秒，或 P95 落在 `+Inf` 桶。

增量取 KV 压力和队列压力计算结果的较大值，至少一个、最多四个，再限制到副本上限。
KV 大于 0.9 时增量为 `int((usage - 0.7) / 0.1)`；队列增量为
`max(1, (total_queue - replicas * 10) // 20)`。只需部分有效指标可支持扩容，
但有效副本指标覆盖率至少为 50%。有扩缩、退休、生成暂停或权重事务时不发起新操作。

## 缩容

所有条件持续 120 秒才考虑缩容：完整有效副本指标覆盖、平均 KV 小于 0.3、无排队、吞吐稳定。
吞吐使用 generation token 计数器增量计算；最近最多十次观测的最大吞吐偏差除以均值小于 0.1。
零吞吐但完整可观测时相对偏差视为零；启动或计数器重置后先取得至少三次有效吞吐观测。

每次只减少一个，且 `平均KV * N / (N - 1) <= 0.5`。不要求训练库存持续高于下一批，
不再执行库存换代 trial。执行仍会停止派发、排空在途请求，确认通信组退休后才停止进程并释放设备。
基础副本不可缩减，权重更新与拓扑操作互斥。排空失败时沿用已有安全回退，不强杀仍在服务的副本。

## 时间及兼容边界

先保留 Relax 的秒级基线：扩容后冷却 60 秒，缩容后冷却 300 秒。冷却按上一次操作方向选择，
期间两个方向均不执行，这是参考方案的行为；本轮未改成按 step。指标陈旧、采样中断、
拓扑变化会重新收集连续证据，重复读取同一份观测不能累积持续时间。

原生 verl 默认自动启动策略，无需额外开关；独立 CLI 需要 `--activate`。
旧 `policy_mode=pipeline` 保留为显式兼容路径，继续使用旧 observer/trial 语义，不是新默认方案。
`pipeline_enabled` 不参与新服务负载判据。

与 Relax 的适配差异：采样沿用现有 5 秒循环；缺失指标不补零；吞吐率首次或重置后有观测预热；
vLLM 采用增量直方图估计延迟；资源释放继续遵守现有 Direct NCCL/HCCL 退休协议。
新副本仍需下一次训练权重同步才能接流量；原生入口仍在首次新策略提交后启动 autoscaler。
因此最小副本必须能完成首批 rollout，本轮不解决首批启动时的提前扩容问题。

这是策略及执行路径的实现调整；CPU/HTTP 测试不等于 GPU/NPU 自动扩缩收益验收。
